**الإصدار:** 1.0  
**التاريخ:** 2026-04-24  
**المرجع:** تفصيل تسلسل العمل بعد [01-master-plan.md](./01-master-plan.md).

## ملخص

تسلسل **عصري** للبناء: **تثبيت المشروع وتشغيله أولاً** → **هيكل التطبيق الأساسي (layout)** → **تصميم الصفحات والترجمة (shell + i18n)** → **ثم** المنطق وقاعدة البيانات والميزات. الهدف: واجهة **نظيفة**، **UX/UI قوي**، وبنية كود **قابلة للصيانة** قبل تعقيد البيزنس.

## المبادئ العامة (تُطبَّق من المرحلة 1)

| المبدأ                     | المعنى العملي                                                                                                               |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **UI قبل اللوجيك للشاشات** | كل شاشة تبدأ كـ **قشرة**: تخطيط، حالات فارغة/تحميل، نصوص من i18n — بدون ربط SQLite أو حسابات معقدة في نفس الخطوة.           |
| **i18n من اليوم الأول**    | لا نص عربي/إنجليزي “محرّف” في JSX؛ مفاتيح + `ar` / `en` + اتجاه `dir` حسب اللغة.                                            |

| **كود نظيف**               | مكوّنات صغيرة، تسمية واضحة، فصل: **واجهة / تنسيق** عن **منطق الجلب** لاحقاً (hooks أو طبقة خدمات).                          |

## المرحلة 1 — تسطيب المشروع وتشغيله (Bootstrap)

**الهدف:** مستودع يُبنى ويُشغَّل محلياً بنفس الأمر على أي جهاز تطوير.

### المخرجات

- **Electron + React + TypeScript** (يفضّل قالب **Vite** لسرعة HMR وتجربة تطوير حديثة).
- سكربتات واضحة في `package.json`: `dev` (تشغيل مع إعادة تحميل)، `build` (بناء تطبيق قابل للتوزيع لاحقاً).
- **Lint + Format** (مثلاً ESLint + Prettier) بإعدادات صارمة من البداية — لا تأجيل “للآخر”.
- ملف `.gitignore` مناسب (`node_modules`، مجلدات build، ملفات بيئة محلية).
- دليل قصير في `docs/guides/` (لاحقاً): “كيف أشغّل المشروع” — يُضاف بعد اكتمال المرحلة 1 فعلياً.

### معايير نجاح المرحلة

- مطوّر جديد: `npm install` ثم `npm run dev` → يفتح التطبيق بدون خطوات يدوية غير موثقة (انظر [guides/dev-setup.md](../guides/dev-setup.md)).

### قائمة المهام (تتبع يومي)

استخدم ملف **[02-implementation-checklists.md](./02-implementation-checklists.md)** — قسم **Phase 1 — Bootstrap** — وضع `[x]` على كل بند عند الإنجاز.

## المرحلة 2 — الهيكل الأساسي (App shell / Layout)

**الهدف:** إطار التطبيق الثابت: تنقل، مناطق الشاشة، تجربة استخدام أساسية — **بدون** شاشات بيزنس مكتملة.

### المخرجات

- **توجيه (Routing)** للشاشات الرئيسية كـ **عناوين placeholder** (مثلاً: لوحة، POS، منتجات، ديون، إعدادات) — المحتوى داخلي لاحقاً.
- **Layout أساسي**: شريط جانبي أو تبويبات علوية (حسب قرار تصميم واحد موثّق)، منطقة محتوى، منطقة إجراءات إن لزم.
- **دعم RTL/LTR على مستوى الجذر** حسب لغة الواجهة (غلاف واحد يضبط `dir` و`lang`).
- **طبقة theme**: متغيرات CSS للألوان والمسافات والخط؛ **وضع فاتح** كبداية (الوضع الداكن اختياري لاحقاً بنفس الرموز).

### معايير نجاح المرحلة

- التنقل بين المسارات يعمل؛ التخطيط لا ينكسر عند تبديل اللغة / الاتجاه.

---

## المرحلة 3 — التصميم: صفحات وقشرة UX (قبل اللوجيك)

**الهدف:** مظهر **عصري ونظيف**، حالات واجهة كاملة، **بدون** ربط بقاعدة البيانات بعد.

### المخرجات

- **مكوّنات واجهة أساسية** قابلة لإعادة الاستخدام: أزرار، حقول إدخال، بطاقات، جداول بسيطة (عرض فقط أو بيانات وهمية).
- **صفحات placeholder** لكل مسار رئيسي: نفس التخطيط، **محتوى توضيحي** أو **حالة فارغة جميلة** (empty state) — يوحّد الشعور بالمنتج.
- **تسلسل بصري واضح**: تباين للقراءة، تباعد متسق، تركيز لوحة مفاتيح للحقول المهمة لاحقاً (POS).
- توثيق مختصر في `docs/architecture/` (اختياري): لقطة قرار “مكتبة مكوّنات vs مكوّنات داخلية” — لتفادي التردد لاحقاً.

### معايير نجاح المرحلة

- أي مسار من المسارات الرئيسية يبدو “جاهزاً للمنتج” بصرياً حتى لو البيانات ثابتة أو وهمية.

### تتبع صفحة بصفحة

استخدم **[03-page-content-design.md](./03-page-content-design.md)** — قسم كل مسار — وضع `[x]` على البنود عند إنهاء تصميم محتوى تلك الصفحة.

## المرحلة 4 — الترجمة (i18n) قبل منطق البيزنس

**الهدف:** كل ما يظهر للمستخدم **عبر مفاتيح**؛ العربية والإنجليزية متكافئتان.

### المخرجات

- إعداد **i18n** (مثلاً `react-i18next` أو بديل مناسب لـ React) مع ملفات `ar` و`en`.
- **مفاتيح منظمة** حسب المسار أو المجال: `nav.*`, `pos.*`, `common.*` — تجنّب ملف ترجمة واحد ضخم بدون تقسيم.
- تمرير **تنسيق الأرقام والعملات** عبر واجهة موحّدة (حتى لو القيم وهمية في البداية) — يهيئ مرحلة POS لاحقاً.
- مراجعة يدوية: لا قصّ نصوص في RTL؛ لا تراكب في LTR.

### معايير نجاح المرحلة

- تبديل اللغة يغيّر كل النصوص الظاهرة في القشرة الحالية دون بقاء “hard-coded strings”.

## المرحلة 5 — المنطق وقاعدة البيانات (بعد اكتمال الواجهة القشرية)

**الهدف:** ربط SQLite، الترحيلات، IPC، POS، ديون، جرد — **طبقة طبقة** مع الحفاظ على نظافة الواجهة.

### تسليق مقترح داخل المرحلة 5

1. **SQLite + ترحيلات** منطقية (انظر `01-master-plan` وقواعد الترحيل في `deken-core.mdc`).
2. **طبقة وصول للبيانات** (queries) منفصلة عن مكوّنات React.
3. **ميزات المنتج** حسب الأولوية في الخطة الرئيسية: منتجات/جرد → POS → ديون → تقارير.

### معايير نجاح المرحلة

- الواجهة لا تتضخم بمنطق SQL؛ الاختبارات أو التحقق اليدوي للمسارات الحرجة يُوثَّق تدريجياً في `docs/guides/`.

## ملخص الترتيب (للمراجعة السريعة)

```
1 Bootstrap     → مشروع يعمل + جودة أدوات (lint/format)
2 Layout        → shell + routing + theme + RTL/LTR
3 Design shell  → مكوّنات + صفحات + empty states (بدون DB)
4 i18n          → كل النصوص عبر مفاتيح ar/en
5 Logic + DB    → SQLite + IPC + ميزات البيزنس
```
