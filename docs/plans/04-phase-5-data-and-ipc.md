## الهدف الاستراتيجي

- ملف **SQLite** واحد (أوفلاين)، **ترحيلات** (migrations) واضحة ومرقّمة.
- **main process** يملك الوصول لقاعدة البيانات؛ **Renderer** يتعامل عبر **preload** آمن فقط (بدون `nodeIntegration: true` في صفحات React دون قرار architecture).
- **فصل** استعلامات/أوامر SQL عن مكوّنات واجهة (طبقة وصول بيانات أو وحدات خدمات قابلة للاختبار لاحقاً).
- **ترتيب ميزات المنتج** (مطابق أولوية 01/02):

  1. **منتجات / جرد** (تعريف أصناف وأسعار ومخزون)  
  2. **POS** (سطر فاتورة يقرأ من الكتالوج؛ دفع / دين)  
  3. **ديون** (رصيد عميل مرتبط بحركات)  
  4. **تقارير** (تجميعات فوق البيانات المخزّنة)  
  5. **إعدادات** تثبّت في تخزين (عملة، اسم محل، طباعة لاحقاً)

---

## تسلسل العمل المقترح (شرائح)

### 5.1 — أساس: قاعدة + ترحيل + مسار DB

- اختيار/تأكيد مكتبة SQL في **main** (مثلاً `better-sqlite3` لـ Electron مع تجميع ناجٍ).
- **مسار ملف** قاعدة بيانات معقول (مجلد بيانات المستخدم/التطبيق) — يُوثّق في دليل لاحق تحت `docs/guides/`.
- **عدّاد ترحيل** جدول `schema_migrations` (أو ما يعادلها) + تشغيل ملفات SQL بالترتيب.
- **سياسة الترحيل** كما في `01-master-plan` و`deken-core.mdc` (واحد = تغيير متماسك، أسماء واضحة).
- اختبار يدوي: تطبيق ذو قاعدة **فارغة** + ترقية من إصدار أقدم (حتى ولو مبدئياً “نسخة واحدة” فقط).

### 5.2 — IPC و preload (عقد ثابت)

- تعريف **قائمة واجهات** `contextBridge` (مثلاً: `getProducts`, `createSale`, `getDebtors` …) — أسماء إنجليزية، أحمال JSON قابلة للتسلسل.
- **TypeScript** مشترك: أنواع الطلب/الرد بين main و renderer (يُوضع تحت `src/shared/` أو حسب [deken-repository-layout](../../.cursor/rules/deken-repository-layout.mdc) عند الإنشاء).
- معالجة أخطاء قابلة للاتساق (كود/رسالة) لتظهر لاحقاً عبر i18n في الواجهة.
- اختصار: لا **SQL** من الـRenderer مباشرة.

### 5.3 — نموذج بيانات أدنى (MVP) لأول بيع حقيقي

- جداول مقترَحة كبداية (يُراجع تفصيل أسماء الحقول أثناء أول ترحيل):

| الجانب        | مضمون أدنى (لـ MVP) |
|---------------|----------------------|
| منتج          | `sku`/`barcode`، اسم، سعر LBP (ولاحقاً USD اختياري)، كمية مخزون |
| عميل (دين)   | اسم، هاتف اختياري، مفتاح |
| بيع/فاتورة   | تاريخ/وقت، إجمالي، نوع دفع (نقدي/دين)، ربط بعميل عند الدين |
| سطر بيع     | فاتورة، منتج، كمية، سعر الوحدة، مجمل السطر |
| دين/حركة    | (اختياري في أول شريحة) دفتر حركات رصيد |

- **لا** تكديس كل الميزات في أول PR: ابدأ بعمق **منتج + جرد** ثم اربط POS.

### 5.4 — ربط الواجهة (بترتيب)

1. **المنتجات** (`ProductsPage`): قراءة/إدراج/تعديل مجرّد من DB (أزرار تُفعّل تدريجياً)؛ استبدال `MOCK_PRODUCTS`.
2. **نقطة البيع** (`PosPage`): استعلام منتج بالرمز/الباركود، خصم من المخزون عند إتمام البيع، دفع نقدي يختم الفاتورة.
3. **دفتر الدين** (`DebtsPage` + مربع الدين في POS): حفظ بيع «على الحساب» يربط **عميل** و**مبلغ** + ملاحظة؛ عرض رصيد من الاستعلام.
4. **التقارير**: تجميعات بسيطة (مبيعات اليوم/الفترة) فوق نفس البيانات.
5. **الإعدادات**: تخزين **اسم المحل**، **سعر صرف تجريبي**، لاحقاً طباعة.

### 5.5 — اختبارات وتوثيق

- اختياري مبكر: اختبارات **main** لطبقة الاستعلام (أو `vitest` على وحدات خالصة).
- عند أول ميزة تلزم **النسخ الاحتياطي** لملف DB: دُرج تحت `docs/guides/` (وليس داخل نفس الـPR إن كانت ضخمة).
- **ADR** اختياري: قرار `better-sqlite3` + مسار الملف (تحت `docs/architecture/` عند الاستقرار).
